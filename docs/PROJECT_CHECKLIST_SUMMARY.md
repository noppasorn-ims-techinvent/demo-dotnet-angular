# สรุปโปรเจกต์ Marketplace Demo — เทียบกับรายการสกิลที่กำหนด

เอกสารนี้สรุปว่า **เว็บหน้า (Angular)** กับ **เซิร์ฟเวอร์ (.NET)** ทำอะไร **ทำไมทำแบบนั้น** และ **ตรงกับรายการสกิลข้อใด** รวมถึงข้อที่ **โปรเจกต์ยังไม่ได้ทำครบ** และ **ต่างจากที่เลือกอย่างไร**

---

## ภาพรวมโปรเจกต์

| ชั้น | ใช้อะไร | ทำหน้าที่อะไร |
|------|---------|----------------|
| หน้าเว็บ | Angular, Bootstrap, แจ้งเตือน, SignalR (ฝั่งเบราว์เซอร์) | ร้านค้า, ตะกร้า, จ่ายเงิน, ออเดอร์, หน้าร้าน/แอดมิน, อัปเดตแบบทันที |
| เซิร์ฟเวอร์ | .NET 8 API, ฐานข้อมูลผ่าน Entity Framework, ล็อกอินด้วยโทเคน, บันทึก log | ให้ API, ส่งข้อความทันที, คิวในหน่วยความจำ, ปรับโครงตารางอัตโนมัติ |
| ตอนพัฒนา | ไฟล์พร็อกซี, คำสั่งรันแอป | ให้เว็บหน้าเดียวกับ API ได้ง่าย ไม่ต้องจัดการเรื่องข้ามเว็บเองทุกจุด |

## เว็บหน้า (Angular) — ทำอะไร / ทำไม / ตรงหัวข้อไหน

### โครงแอป: หน้าจอ + บริการ (แบบ **Standalone**)

- **ทำอะไร:** แอปสตาร์ทจากไฟล์ config หลัก ไม่พึ่งโมดูลใหญ่แบบเก่า; แต่ละหน้า/ฟีเจอร์ประกาศว่าใช้ของอะไรเอง และดึงบริการด้วยฟังก์ชัน inject ของ Angular
- **ทำไม:** เขียนสั้นลง โหลดหน้าทีหลังได้ตรง ๆ โดยไม่ต้องห่อเป็นโมดูลใหญ่
- **Checklist:** ตรง **Component, Service** — **ไม่ได้ทำแบบ NgModule + loadChildren** เพราะเลือก standalone ทั้งแอป (ดูตาราง “ไม่มีในโปรเจกต์”)

### จังหวะชีวิตของหน้าจอ (Lifecycle hooks)

- **ทำอะไร:** ใช้จังหวะเริ่มโหลดข้อมูล, จังหวะที่ข้อมูลจากด้านบนเปลี่ยน, และจังหวะหลังวาดหน้าจอเสร็จ (เช่น หน้ารายละเอียดสินค้า, ชำระเงิน, ฟอร์มสินค้าร้าน)
- **ทำไม:** โหลดข้อมูลหรือเลือกช่องกรอกตอนที่ “พร้อมแล้ว” ไม่เร็วหรือช้าเกินไป
- **Checklist:** **Lifecycle Hooks**
- **อธิบายละเอียด:** ด้านล่างมีหมวด **ทำไมถึงทำแบบนี้** (โดยเฉพาะการ์ดสินค้า — จับเวลาที่ข้อมูลจากด้านบนเปลี่ยน)

### การส่งข้อมูลระหว่างหน้าจอ

- **ข้อมูลลงมา (Input):** เช่น การ์ดสินค้ารับข้อมูลสินค้าจากรายการด้านบน
- **เหตุการณ์ขึ้นไป (Output):** เช่น การ์ดสินค้าบอกแม่ว่า “กดใส่ตะกร้า” พร้อมจำนวน
- **อ้างช่องในแบบฟอร์ม/หน้าจอ:** เช่น โฟกัสช่องชื่อสินค้า, หรือมีหลายช่องจำนวนในหน้าชำระเงิน
- **บริการกลาง:** ล็อกอิน, ออเดอร์, การเชื่อมต่อแบบทันที, ตะกร้า, ค่าตั้งต้นแอป
- **Checklist:** **@Input, @Output, ViewChild, Shared Service**

### แบบฟอร์มแบบเขียนเป็นโค้ด (Reactive Forms)

- **ทำอะไร:** ล็อกอิน, สมัคร, ชำระเงิน (มีหลายแถวสินค้า), จ่ายเงินจำลอง, ฟอร์มสินค้าร้าน — มีการตรวจค่าก่อนส่ง
- **ทำไม:** ฟอร์มยาว ๆ ควบคุมง่ายกว่าแบบผูกในหน้า HTML ล้วน ๆ
- **Checklist:** **Reactive Forms**

### เส้นทางหน้า, กันไม่ให้เข้า, โหลดก่อนเข้า, โหลดทีหลัง

- **ทำอะไร:** ไฟล์เส้นทางหลัก — โหลดหน้าเป็นชิ้น ๆ; กันคนไม่ล็อกอิน, กันคนที่ไม่ใช่ร้าน/แอดมิน; โหลดข้อมูลสินค้าก่อนเข้าหน้ารายละเอียด
- **ทำไม:** แยกสิทธิ์ชัด และไม่ให้เข้าหน้าที่ยังไม่มีข้อมูล
- **Checklist:** **Routing / Guard / Resolver / Lazy Loading** (ตัวอย่าง “โหลดก่อนเข้า” เน้นที่สินค้า)

### สิทธิ์ / เซสชัน

- **ทำอะไร:** เก็บโทเคนล็อกอินในเบราว์เซอร์; ทุกคำขอไป API แนบโทเคน; ถ้าเซิร์ฟเวอร์บอกหมดอายุ (401) ให้ออกจากระบบ (ยกเว้นหน้าเข้าสู่ระบบ/สมัคร)
- **ทำไม:** แยกผู้ซื้อ / ร้าน / แอดมิน
- **Checklist:** **Authorization / Session Handling**

### เรียก API + ตัวกลางแก้คำตอบ

- **ทำอะไร:** ตัวกลางฝั่งเบราว์เซอร์แปลงคำตอบจากเซิร์ฟเวอร์ที่ห่อชุดมาตรฐาน (สำเร็จ/ข้อความ/รหัสติดตาม/ข้อมูลจริง) ให้เหลือแค่ “ข้อมูลจริง” ที่หน้าจอใช้; ข้ามพาธ hub สุขภาพระบบ; อีกตัวแนบโทเคนล็อกอิน
- **ทำไม:** ทุกหน้าไม่ต้องเขียนถอดห่อซ้ำ ๆ
- **Checklist:** **HttpClient / Interceptor**

### RxJS (จัดการงานที่รอผล)

- **ทำอะไร:** จัดการขั้นตอนหลังได้ผล, จับข้อผิดพลาด, ยิงหลายคำขอพร้อมกันแล้วรอครบ (เช่น แอดมินเปิดรายละเอียดออเดอร์รอยกเลิก), รอค่าครั้งเดียวตอนเปิดแอป
- **ทำไม:** งานแบบรอเครือข่ายทำเป็นขั้น ๆ อ่านง่าย
- **Checklist:** **RxJS**

### รันก่อนเปิดหน้าหลัก (APP_INITIALIZER)

- **ทำอะไร:** ตอนเปิดแอป — ดึงค่าตั้งจาก API, คืนสถานะล็อกอิน, เชื่อมแชทแบบทันทีถ้ามีสิทธิ์
- **ทำไม:** ให้พร้อมก่อนผู้ใช้เริ่มกด
- **Checklist:** **APP_INITIALIZER**

### SignalR (ข้อความทันที)

- **ทำอะไร:** ฝั่งเซิร์ฟเวอร์มี hub; ฝั่งเว็บมีบริการคุยกับ hub — ออเดอร์ สต็อก ยกเลิก ฯลฯ; พร็อกซีตั้งให้รองรับการเชื่อมแบบทันที
- **ทำไม:** ไม่ต้องให้เว็บถามเซิร์ฟเวอร์ซ้ำ ๆ เป็นระยะเพื่อดูว่ามีอัปเดตหรือยัง
- **Checklist:** **SignalR** — **ไม่ได้สาธิต WebSocket แบบเขียนเองทั้งเส้น** เพราะ SignalR ครอบงานนี้ได้แล้ว

### ความเร็วหน้าเว็บ

- **ทำอะไร:** โหมดประหยัดการอัปเดตหน้า, บอกว่าแถวไหนคือสินค้าเดิม, และเลื่อนวาดรายการสินค้าจนเบราว์เซอร์ว่าง
- **ทำไม:** รายการยาวจะได้ไม่หน่วง
- **Checklist:** **Performance Optimization** (ไม่ได้ใช้โหมดประหยัดทุกหน้า)

### ไฟล์โครงแอป Angular

- **มี:** หน้าเริ่ม, จุดสตาร์ทแอป, ค่าตั้งโปรเจกต์, ค่าแวดล้อม (พัฒนา/ใช้งานจริง)
- **Checklist:** **Angular Files** — ครบ

### หน้าจอสำคัญ (สั้น ๆ)

| พื้นที่ | หน้าที่ |
|---------|---------|
| ร้านค้า / รายละเอียดสินค้า | แคตตาล็อก, ตะกร้าผู้ซื้อ, โหลดข้อมูลก่อนเข้าหน้ารายละเอียด |
| ชำระเงิน | แบบฟอร์มแบบโค้ด, จ่ายเงินจำลอง |
| คำสั่งซื้อของฉัน | รายการสินค้า, ขอยกเลิก, บอกว่าแยกมาจากออเดอร์ไหน |
| ร้านค้า (Seller) | สต็อก, ออเดอร์เข้าร้าน, พิจารณายกเลิก |
| แอดมิน | รายการออเดอร์, ชื่อผู้ซื้อ, รายการสินค้า, พิจารณายกเลิกแยกร้าน, ลบออเดอร์ |

## เซิร์ฟเวอร์ (.NET) — ทำอะไร / ทำไม / ตรงหัวข้อไหน

### ชั้น API / กฎธุรกิจ / อ่านเขียนฐานข้อมูล

- **ทำอะไร:** คลาสรับคำขอ HTTP; กฎออเดอร์ สินค้า ล็อกอินอยู่ในบริการ; การอ่านเขียนตารางอยู่ในชั้นที่เรียกฐานข้อมูล
- **ทำไม:** แยก “รับส่ง HTTP” กับ “คิด” กับ “เก็บข้อมูล” อ่านง่าย
- **Checklist:** **Controller / Service / Repository**

### รูปแบบคำตอบ + ข้อมูลที่ส่งกลับ (DTO)

- **ทำอะไร:** นิยามชุดข้อมูลออเดอร์/บรรทัดออเดอร์ ฯลฯ; เซิร์ฟเวอร์ห่อคำตอบเป็นชุดเดียวกัน (สำเร็จ/ข้อความ/รหัสติดตาม/ข้อมูล)
- **ทำไม:** หน้าเว็บรู้รูปแบบเดียวกันทุก API
- **Checklist:** **ActionResult / DTO**

### Entity Framework, คำสั่งถามข้อมูล, โหลดข้อมูลที่เกี่ยวข้อง

- **ทำอะไร:** บอกชัดว่าต้องดึงตารางไหนพร้อมกัน; โหมดอ่านอย่างเดียวไม่ติดตามการแก้ใน memory; แยกคำถามใหญ่เป็นสองชุดในบางกรณี; **ไม่ใช้โหลดแบบเลื่อนอัตโนมัติแบบ proxy** — โหลดตอนถามชัด ๆ
- **ทำไม:** ลดการถามฐานข้อมูลซ้ำ ๆ โดยไม่ตั้งใจ และรู้ขนาดคำถาม
- **Checklist:** **EF Core / LINQ** — **ไม่ได้ใช้ lazy load แบบ proxy** (ตั้งใจโหลดชัด)

### เขียนโมเดลก่อน แล้วค่อยสร้างตาราง (Code First + Migration)

- **ทำอะไร:** นิยามตารางในโค้ด แล้วให้เครื่องมือสร้าง/อัปเดตตาราง; ตอนเริ่มแอปจะรัน migration
- **ทำไม:** โครงตารางตามโค้ด ทีมเดียวกับแอป
- **Checklist:** **Code First / DB Migration**

### Database First

- **ใน checklist:** สร้างโค้ดจากฐานข้อมูลที่มีอยู่แล้ว  
- **ในโปรเจกต์:** **ไม่ได้สาธิตแบบนี้จริง** — ใช้แนวเขียนโมเดลก่อนเป็นหลัก  
- **ต่างกันอย่างไร:** เลือกแบบง่ายสำหรับตัวอย่าง

### SQL / ดัชนี / ปรับคำถาม

- **ทำอะไร:** มีดัชนีช่วยค้น (ผู้ซื้อ, อีเมล, ออเดอร์ ฯลฯ); ไม่ได้เน้นสคริปต์ SQL ยาว ๆ หรือ stored procedure
- **Checklist:** **SQL / Query Optimization / Index** — มีดัชนีผ่านเครื่องมือ EF; **ไม่ได้แยกไฟล์ SQL ปรับมือเป็นจุดขาย**

### async / await

- **ทำอะไร:** คำขอ API และบริการรอฐานข้อมูล/SignalR แบบไม่ไปบล็อกเธรดหลัก
- **Checklist:** **async / await**

### การส่งบริการเข้าไปในแอป (Dependency Injection)

- **ทำอะไร:** ลงทะเบียนบริการ ที่เก็บข้อมูล hub ตรวจสุขภาพ ในไฟล์เริ่มแอป
- **Checklist:** **Dependency Injection**

### ธุรกรรมฐานข้อมูล (Transaction)

- **ทำอะไร:** เริ่ม “ก้อนเดียว” ตอนพิจารณายกเลิกหรือลบออเดอร์ที่แตะหลายตาราง
- **ทำไม:** ถ้าคั่นกลางพัง ให้ **ยกเลิกทั้งก้อน** ไม่ให้ข้อมูลค้างครึ่งทาง
- **Checklist:** **Transaction**

### คิว (Queue)

- **ทำอะไร:** คิวในหน่วยความจำ + งานพื้นหลังรับไปประมวลผล  
- **ทำไม:** จำลองว่า “สั่งซื้อแล้วมีคนประมวลผลอีกคน” โดยไม่ต้องติดตั้งโปรแกรมคิวภายนอก
- **Checklist:** **Queue / Channel** — **ไม่มี RabbitMQ** (ดูตารางด้านล่าง)

### ล็อกอิน, สิทธิ์, ข้ามเว็บ, รหัสผ่าน

- **ทำอะไร:** โทเคน Bearer; บอกบทบาทในตัวโทเคน; อนุญาตเว็บอื่นเรียกตาม config; เก็บรหัสผ่านแบบแฮช
- **ทำไม:** รู้ว่าใครเรียก API และเป็นใครบ้าง
- **Checklist:** **JWT / Authentication / Authorization / CORS / Hash & Salt**

### บันทึก log

- **ทำอะไร:** NLog + รหัสติดตามคำขอ (จาก header หรือจากระบบ)
- **ทำไม:** ตามหา log ของคำขอเดียวกันได้
- **Checklist:** **Logging (NLog)**

### รหัสติดตาม / หน้าทดสอบข้อผิดพลาด

- **ทำอะไร:** อ่านรหัสติดตามจากคำขอ; มี endpoint ทดสอบดูรหัส; **ข้อผิดพลาดหลัก** ส่งเป็น JSON รูปแบบมาตรฐานผ่านตัวจับข้อผิดพลาดกลาง  
- **ทำไม:** แยก “ดูรหัสติดตาม” กับ “จัดการ error ทั้งแอป” ชัด
- **Checklist:** **ErrorController / ITrace** — เน้นแบบ **API + ตัวจับ error** ไม่ใช่ redirect ไปหน้า error แบบเว็บ MVC เก่า

### ตรวจว่าระบบพร้อมไหม (Health checks)

- **ทำอะไร:** พาธ `/health` ฯลฯ — เช็กว่าต่อฐานข้อมูลได้ และเช็กตัวเอง
- **ทำไม:** เอาไปใช้ตอน deploy หรือมอนิเตอร์ว่า “พร้อมรับงานไหม”
- **Checklist:** **Health check**

### IWebHostEnvironment

- **ใน checklist:** อ่าน path หรือสภาพแวดล้อมจาก host  
- **ในโปรเจกต์:** ใช้การอ่านค่าจากไฟล์ config เป็นหลัก **ยังไม่ฉีด IWebHostEnvironment เข้าบริการ**  
- **ต่างกัน:** พอสำหรับตัวอย่าง; ถ้าต้องอ่าน path ไฟล์บนเซิร์ฟเวอร์ชัด ๆ ค่อยเพิ่มทีหลัง

### ห่อคำตอบมาตรฐาน (ApiResponse)

- **ทำอะไร:** โมเดลห่อ + ตัวกรองห่อทุกคำตอบ; ฝั่งเว็บมีตัวถอดห่อ
- **ทำไม:** รูปแบบเดียวกันทั้งทีม
- **Checklist:** เสริมจากชุดเดิม — ไม่ใช่ของมาตรฐาน ASP.NET ล้วน ๆ

### เรื่องธุรกิจสำคัญ (สั้น ๆ)

- **ออเดอร์:** สร้าง, จ่ายจำลอง, ขอยกเลิก, ร้านพิจารณา (อนุมัติ = เอาบรรทัดออก + คืนสต็อก / ไม่อนุมัติ = แยกเป็นออเดอร์ลูก), บาง flow จบแล้วออเดอร์แม่อาจเป็น **ยกเลิก** ว่างบรรทัด แทนการลบแถวในตารางออเดอร์  
- **SignalR:** แจ้งสถานะออเดอร์ ยกเลิก สินค้า ร้าน  
- **ผู้ใช้:** สมัคร/ล็อกอิน, บทบาทจากข้อมูลเริ่มต้น

## หัวข้อใน checklist ที่ “ไม่มีหรือไม่ตรง” ในโปรเจกต์ — คืออะไร / ต่างจากที่ทำอย่างไร

| หัวข้อ | โดยทั่วไปคือ | ในโปรเจกต์นี้ |
|--------|----------------|----------------|
| **NgModule + loadChildren** | แบ่งแอปเป็นโมดูลใหญ่ แล้วโหลดทีหลัง | ใช้ **standalone + โหลดหน้าเป็นชิ้น** แทน — ได้ผลคล้ายกัน (โหลดทีหลัง แยกไฟล์) แต่ไม่ใช่แบบโมดูลเก่า |
| **RabbitMQ** | คิวภายนอก ข้อความอยู่ถ้าเซิร์ฟเวอร์รีสตาร์ท | ใช้ **คิวในหน่วยความจำ** — ง่ายสำหรับตัวอย่าง ไม่ต้องลง RabbitMQ; ถ้าเซิร์ฟเวอร์ดับ ข้อความในคิวหาย |
| **Database First** | เขียนโค้ดจากฐานข้อมูลที่มีอยู่ | ใช้ **เขียนโมเดลก่อน** + migration |
| **EF Lazy loading proxies** | โหลดข้อมูลย่อยทีหลังอัตโนมัติ | ใช้ **บอกชัดว่าจะโหลดอะไร** — ควบคุมง่ายกว่า |
| **WebSocket ดิบ** | เขียนการเชื่อมต่อเองทั้งเส้น | ใช้ **SignalR** ซึ่งจัดการชั้นล่างให้ — ไม่ซ้ำสอน socket ดิบ |
| **IWebHostEnvironment ในโค้ด** | อ่าน path หรือสภาพแวดล้อมจาก host | ยังไม่ใช้ในบริการ — ใช้ไฟล์ config แทน |
| **ErrorController แบบส่งไปหน้า error** | พอ error แล้ว redirect ไป controller | ใช้ **ตัวจับ error + ส่ง JSON** — เหมาะ API มากกว่า |

## ทำไมถึงทำแบบนี้ (อธิบายแบบเข้าใจง่าย)

หัวข้อนี้ขยายจากด้านบน โดยเน้นว่า **จังหวะของหน้าจอ**, **เวลาที่ข้อมูลจากด้านบนเปลี่ยน**, และ **ทางเลือกฝั่งเซิร์ฟเวอร์** ทำไมถึงเหมาะกับโปรเจกต์ตัวอย่างนี้

### เวลาที่ “ข้อมูลจากด้านบนเปลี่ยน” — การ์ดสินค้า

- **เรียกเมื่อไหร่:** เมื่อหน้าด้านบนส่งข้อมูลสินค้าเข้ามาที่การ์ด **เปลี่ยน** (เช่น เปลี่ยนเป็นสินค้าอื่น หรือส่งชุดข้อมูลใหม่)
- **ทำไมมีในโปรเจกต์:** เป็นตัวอย่างว่าเรารู้จัก **จังหวะนี้** ตามรายการสกิล — ใช้จับว่า “ด้านบนอัปเดตลงมาแล้ว”
- **เกี่ยวกับโหมดประหยัด (OnPush):** แอปไม่คอยเช็กทุกจุดบนหน้าบ่อยเหมือนโหมดปกติ; เวลาข้อมูลเปลี่ยนจากด้านบนเป็นชุดใหม่ นี่คือจุดที่รู้ได้ชัดว่า “ของที่แสดงเปลี่ยนแล้ว” และยังรู้ได้ว่าเป็นครั้งแรกหรือครั้งถัดไป
- **ในโค้ดตอนนี้:** ฟังก์ชันนี้ **เกือบว่าง** — เป็นแค่ตัวอย่าง ไม่ได้ใช้คิดธุรกิจจริง; ถ้าต่อยอดจริงมักใช้เวลาต้อง **รีเซ็ตค่าภายในการ์ด** เมื่อสินค้าเปลี่ยน หรือบันทึก log
- **ต่างจากจังหวะ “เริ่มครั้งเดียว”:** จังหวะเริ่มรันหลังสร้างการ์ด **ครั้งเดียว** — ไม่รู้ว่าด้านบนจะส่งสินค้าใหม่รอบหลัง; จังหวะ “ข้อมูลเปลี่ยน” รัน **ทุกครั้งที่ด้านบนส่งของใหม่**

### จังหวะ “เริ่มโหลดข้อมูล” — หน้ารายละเอียด ชำระเงิน

- **เพราะอะไร:** ตอนนี้ค่าจาก URL หรือข้อมูลที่ส่งเข้ามา **พร้อมแล้ว** — เหมาะกับเรียก API โหลดข้อมูล
- **ต่างจากตอนสร้างคลาส:** ช่วงสร้างคลาสยังไม่เหมาะยิงงานเครือข่ายหนัก ๆ; ใช้จังหวะนี้แทน ทีมอ่านง่าย

### หลังวาดหน้าจอเสร็จ + อ้างช่องกรอก — ฟอร์มสินค้าร้าน

- **เพราะอะไร:** ช่องชื่อสินค้ามีตัวจริง **หลัง** หน้าวาดเสร็จ; ถ้าโฟกัสช่องชื่อต้องรอจังหวะนี้ ไม่งั้นอาจโฟกัสไม่โดน

### หลายช่องในหน้าชำระเงิน

- **เพราะอะไร:** มีหลายแถวสินค้า จึงมีหลายช่องจำนวน — ต้องอ้าง **หลายช่องพร้อมกัน** และอัปเดตเมื่อแถวเปลี่ยน

### โหมดประหยัด + บอกว่าแถวไหนคือสินค้าเดิม + เลื่อนวาดรายการ — หน้ารายการสินค้า

- **โหมดประหยัด:** ลดการ “เช็กทั้งหน้าว่าต้องเปลี่ยนไหม” เมื่อรายการยาว
- **บอกแถวเดิม:** ถ้าไม่บอก Angular อาจ **สร้างการ์ดใหม่ทั้งแถว** ทุกครั้งที่รายการเปลี่ยน — ช้าและเสียค่าที่กรอกค้างในการ์ด; บอกด้วยรหัสสินค้า (เช่นเลข id) ว่าแถวไหนคือตัวเดิม
- **เลื่อนวาดรายการ:** ค่อยวาดบล็อกรายการสินค้าหลังเบราว์เซอร์ว่าง — หน้าแรกเปิดเร็วขึ้น (ในตัวอย่างนี้เป็นแนวทางเรื่องความเร็ว)

### แบบฟอร์มแบบโค้ด — ชำระเงิน / ล็อกอิน

- **เพราะอะไร:** ฟอร์มยาว มีหลายแถว มีการตรวจหลายช่อง — เขียนเป็นโครงสร้างในโค้ด **อ่านและแก้ง่ายกว่า** แบบผูกใน HTML ล้วน ๆ

### กันไม่ให้เข้า + โหลดก่อนเข้า

- **กัน:** เช็กสิทธิ์ก่อนเปิดหน้า — ไม่ต้องให้ทุกหน้าเขียนเช็กเองซ้ำ ๆ
- **โหลดก่อน:** ดึงข้อมูลสินค้าก่อนเข้าหน้ารายละเอียด — ลดอาการกระพริบ “ไม่พบ” และถ้าไม่มี id จริง ๆ ก็ล้มทันที

### ตัวกลางสองตัว (ถอดห่อ + แนบโทเคน)

- **เพราะอะไร:** คำขอออกไปมีโทเคนล็อกอิน; คำตอบกลับมาถูก **ถอดห่อมาตรฐาน** ให้เหลือข้อมูลที่หน้าใช้ — หน้าจอไม่ต้องรู้รายละเอียดห่อทุกครั้ง

### SignalR แทนการเขียน WebSocket เอง

- **เพราะอะไร:** มีขั้นตอนเชื่อมต่อ สำรองถ้าเส้นทางหลักใช้ไม่ได้ และแยกกลุ่มผู้ใช้ (ผู้ซื้อ ร้าน แอดมิน) — ไม่ต้องเขียนระบบเชื่อมต่อเองทั้งก้อน

---

### เซิร์ฟเวอร์ — **ธุรกรรมฐานข้อมูล** ตอนพิจารณายกเลิก

- **เพราะอะไร:** คำขอเดียวแตะหลายตาราง (บรรทัดออเดอร์ สต็อก ออเดอร์ลูก สถานะแม่) — ถ้าคั่นกลางพังต้อง **ยกเลิกทั้งก้อน** ไม่ให้สต็อกหรือยอดค้างครึ่งทาง

### เซิร์ฟเวอร์ — **คิวในหน่วยความจำ** แทน RabbitMQ

- **เพราะอะไรในตัวอย่าง:** ไม่ต้องลงโปรแกรมคิวแยก — แต่ยังเห็นภาพว่า “มีคนส่งงาน” กับ “มีคนรับงานพื้นหลัง”
- **แลกมา:** ถ้าเซิร์ฟเวอร์ดับ ข้อความในคิว **หาย**; ไม่มีหลายเครื่องมาช่วยกินคิว — ต่างจาก RabbitMQ ที่ออกแบบให้ทนทานและแชร์หลายเครื่อง

### เซิร์ฟเวอร์ — **บอกชัดว่าจะโหลดอะไร** + **อ่านอย่างเดียวไม่เก็บติดตามในหน่วยความจำ**

- **เพราะอะไร:** รู้ว่าคำถามฐานข้อมูล **กว้างแค่ไหน** ลดการถามซ้ำโดยไม่ตั้งใจ; โหมดอ่านอย่างเดียวเหมาะ API ที่แค่ดึงข้อมูลไปแสดง ไม่ต้องให้โปรแกรมจำแถวไว้แก้ต่อในแรมตามทางนั้น

### เซิร์ฟเวอร์ — **จับข้อผิดพลาดเป็น JSON มาตรฐาน**

- **เพราะอะไร:** เวอร์ชันใหม่ต้องการตัวจับความผิดพลาดชัดเมื่อใช้ตัวจับกลางแบบนี้; คำตอบตอนพังเป็นรูปแบบข้อความมาตรฐาน **เข้าชุดกับคำตอบปกติ** — เหมาะแอปที่เป็นหน้าเดียวมากกว่าส่งผู้ใช้ไปหน้าแสดง error แบบเว็บเก่า

## สรุปหนึ่งย่อหน้า

โปรเจกต์นี้เป็น **ตัวอย่างร้านค้าออนไลน์แบบครบสองฝั่ง** — หน้าเว็บใช้ Angular แบบปัจจุบัน (แยกหน้า, แบบฟอร์ม, เส้นทาง, สิทธิ์, แจ้งเตือนทันที, ตัวกลางเรียก API, รอผลจากเครือข่าย, ตั้งค่าก่อนเปิดแอป, ปรับความเร็วบางจุด) และเซิร์ฟเวอร์ใช้ .NET 8 (แยกชั้นงาน, ฐานข้อมูลผ่านเครื่องมือ migration, ล็อกอิน, อนุญาตข้ามเว็บ, ธุรกรรม, คิวในหน่วยความจำ, log, เช็กพร้อมรับงาน, คำตอบห่อมาตรฐาน, รหัสติดตาม) โดยตั้งใจให้ **รันบนเครื่องเดียวได้ง่าย** และ **อ่านตามรายการสกิลได้** มากกว่าจะครบทุกอย่างแบบระบบใหญ่ (เช่น RabbitMQ, สร้างโค้ดจาก DB ที่มีอยู่, โมดูล Angular แบบเก่า) — ถ้าอยากเติมให้ครบรายการสกิลแบบบริษัท ใช้ตาราง “ไม่มีหรือไม่ตรง” ด้านบนเป็นจุดต่อยอดได้
